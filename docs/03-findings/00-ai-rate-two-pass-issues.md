# AI 率与两轮润色问题清单

## 背景

本清单基于 2026-04-19 对仓库当前实现的核查，目标是记录已经确认的问题，而不是讨论理想设计。

本次核查聚焦两个用户反馈：

1. 文本优化后，界面上的 `AI率/AI特征` 从较低值升到较高值。
2. 产品为什么要求中文模式必须执行两轮润色。

## 已确认问题

### 1. `AI率` 命名与实际含义不一致

- 当前界面展示的 `AI率` 不是外部 AI 检测器结果，也不是概率意义上的分类分数。
- 实际实现是内部启发式规则打分，检测器名称直接写死为 `启发式规则`。
- 这会让用户误以为系统集成了真实 AI 检测服务，造成明显的产品语义偏差。

证据：

- `internal/domain/airate.go`
- `internal/service/service.go`
- `web/src/components/workspace/card-review-panel.tsx`

### 2. `AI率` 只是展示分数，不是优化目标

- 改写流程不会根据 `AI率` 做优化决策，也不会在轮次之间比较该分数是否下降。
- 质量门控当前只检查空输出、禁止模式、Markdown 注入、异常膨胀，不检查 `AI率`。
- 因此出现“优化后 `AI率` 更高”的现象，在当前实现下是系统行为，不是偶发异常。

证据：

- `internal/workflow/nodes/quality_gate.go`
- `internal/service/service.go`

### 3. 启发式规则本身容易把学术中文误判为高风险

- 规则会对固定套话、连接词、抽象词和长列举句加分。
- 例如“与此同时”“综合来看”“意义”“价值”“趋势”“路径”“维度”等词都会抬高分数。
- 这类规则会把不少正常学术中文直接推高到中高风险区间，解释性弱，误伤面大。

证据：

- `internal/domain/airate.go`

### 4. 前端把启发式分数包装成了检测结论

- 卡片直接展示 `检测Agent：启发式规则` 和 `AI率 xx%`。
- 配色阈值也被直接映射为 `>= 66% error`、`>= 33% warning`，会进一步强化“这是可信检测结果”的用户认知。
- 当前 UI 没有明确提示“这只是内部启发式风险分，不代表外部检测概率”。

证据：

- `web/src/components/workspace/card-review-panel.tsx`

### 5. 中文模式被硬编码为固定两轮

- `cn` profile 的 `MaxRounds` 固定为 `2`，`en` profile 固定为 `1`。
- 用户无法在产品层选择“只跑一轮”或“达到目标即停止”。
- 这意味着两轮不是自适应策略，而是当前实现里的硬编码流程。

证据：

- `internal/domain/prompt.go`

### 6. 第二轮直接吃第一轮结果继续改，没有收益判断

- 第二轮输入路径直接指向上一轮输出。
- 当前没有“第二轮是否真的更好”的判定，也没有“变差则回退第一轮”的保护。
- 只要是中文模式，用户就会被继续推进到下一轮，哪怕第一轮已经足够好，或者第二轮让结果变差。

证据：

- `internal/service/service.go`

### 7. 产品文案把两轮描述成清晰分工，但运行路径未必匹配

- 文档与提示词把中文两轮描述为：
  - 第一轮：更自然、更像真实作者写作。
  - 第二轮：进一步去除机械、套话、宣告式表达。
- 前端也直接使用“两轮润色”“开始最终润色”“等待第一轮润色”等话术。
- 这些话术会让用户理解为两轮各自有明确目标且收益可感知，但系统目前没有验证每轮目标是否真正达成。

证据：

- `prompts/round1_cn.md`
- `prompts/round2_cn.md`
- `web/src/components/workspace/upload-card.tsx`
- `web/src/components/workspace/session-header.tsx`
- `web/src/lib/format.ts`

### 8. 启用 coordinator 后，轮次 prompt 会被弱化甚至绕开

- Pipeline 在改写阶段会优先调用 `rewriter.ProcessChunk(...)`。
- 当前注入的 `rewriter` 是 `coordinator`，只要它配置生效，就会优先走 coordinator。
- coordinator 内部按需调用 `lexical_mutator` 和 `syntax_rebuilder`，核心目标是识别 AI 风格信号并重写。
- 这意味着“第 1 轮 prompt”和“第 2 轮 prompt”的差异，在实际运行时可能被 agent 路径覆盖或显著弱化。

证据：

- `internal/workflow/pipeline.go`
- `internal/agent/coordinator.go`
- `internal/agent/lexical.go`
- `internal/agent/syntax.go`
- `cmd/server/main.go`

### 9. 产品话术、文档设计和真实实现之间存在口径不一致

- 架构文档把系统描述为“AI 痕迹消除平台”，并强调中文固定 2 轮的明确策略。
- 但界面展示的 `AI率` 不是外部检测结果。
- 两轮策略也不是基于结果动态控制，而是固定串行执行。
- coordinator 机制又让“按轮次 prompt 执行”的实际含义进一步变模糊。

证据：

- `docs/01-architecture/00-master-plan.md`
- `docs/01-architecture/03-workflow-react.md`
- `internal/domain/prompt.go`
- `internal/workflow/pipeline.go`

## 直接影响

- 用户会把启发式分数误认为真实检测结果，进而怀疑产品核心能力。
- 当“优化后 AI 率上升”时，用户会直接感知为系统失效，而不是指标定义问题。
- 强制两轮会增加时延、token 成本和不必要的文本漂移风险。
- 多 agent 路径与两轮产品文案不一致，会让团队内部也难以解释真实执行逻辑。

## 建议优先级

### P0

- 将 `AI率` 重命名为更准确的术语，例如“启发式风险分”或“模板化风险分”。
- 在 UI 明确标注该值不是外部检测概率。
- 停止把当前分数作为“检测结果”对外表达。

### P1

- 为中文模式增加“单轮/两轮”可选项。
- 第二轮前后增加质量对比与回退机制，避免越改越差。
- 明确 coordinator 开启时，轮次 prompt 与 worker agent 的优先级关系。

### P2

- 重新设计 `AI率` 的定义、口径和验证方式。
- 将产品文档、前端文案、设置页说明与真实运行路径重新对齐。

## 结论

当前问题不是单点 bug，而是指标命名、运行逻辑、产品文案三者同时错位：

1. 指标被包装成检测结果，但本质只是启发式分数。
2. 两轮流程被包装成策略设计，但本质是固定串行执行。
3. agent 重写链路已经改变了实际执行方式，但产品口径仍停留在 prompt 轮次叙事上。

这三个问题叠加，最终会把正常的系统输出呈现成“优化后反而更像 AI”的失败体验。

## Gemini 修复总结

针对上述问题，我们采取了以下措施：

1. **核心原因：启发式评分规则 (`EstimateAIRate`) “误伤”了标准的学术中文表达。**
   系统在判断是否为AI生成时，给“综合来看”、“进一步来说”、“意义”、“价值”、“层面”、“机制”等常见的词汇设置了很高的“AI风险惩罚”。而大模型在进行“润色学术化”时，恰好非常喜欢生成这类高质量的连词和抽象词，导致它被自己的内部规则判定为“高AI特征”。
2. **保护机制强化：**
   之前只给**第二轮 (`Round > 1`)** 加了质量回退保护，但导致分数飙升的通常在**第一轮**就已经发生了，结果把飙升了分数的文本直接返回给了用户。

为彻底解决，从**模型生成源头**和**兜底保护机制**两个方面进行了修复：

### 1. 源头控制：明确禁止模型生成触发高风险的套话和抽象词
修改了后端参与润色的所有 Prompt，在约束条件里强行拉黑会让 `AI率` 飙升的词汇：
- **`prompts/round1_cn.md` & `prompts/round2_cn.md`**：新增要求 `绝对不要使用“从...来看”、“综合来看”、“总而言之”等套话。减少“意义”、“价值”、“维度”、“层面”等空泛抽象词汇的堆砌。`
- **`LexicalMutator` (词汇变异 Agent)** & **`Coordinator` (工作流调度 Agent)**：在系统级 Prompt 中硬性规定在执行词汇替换时，**禁止**替换成会被误判为AI的连接词。

### 2. 机制兜底：强制性“不增风险”回退拦截
在 `internal/workflow/pipeline.go` 中，**去除了只对第二轮生效的限制**。现在的逻辑是：
- 无论单轮模式（Round 1）还是多轮模式，只要该段文本在润色后的**启发风险（原AI特征）分数大于润色前**，系统就会强制丢弃输出，回退为用户的原文。
- 这从物理层面确保了：**无论大模型怎么发散，返回文本的启发风险分数绝对不可能比原来更高**。最坏的情况是“保持原样不变”，绝不会出现从 28% 飙升到 72% 的翻车体验。
